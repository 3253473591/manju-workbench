# 01 · 数据结构

> 权威 DDL 与 JSON schema。改字段只改这里。
> 所有建表语句默认追加 `ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci`，下文省略。
> **不写函数默认值**（如 `DEFAULT CURRENT_TIMESTAMP`）：`DATETIME` 的隐式默认会吃会话时区，全部时间由应用写入 UTC。`DATETIME(3) NOT NULL` 必须显式赋值。

---

## 1. 类型映射

| 概念 | MySQL | Python | TypeScript |
|---|---|---|---|
| 主键/外键 | `BIGINT UNSIGNED` | `int` | `number` |
| 金额 | `DECIMAL(12,6)` | `Decimal` | `string` |
| 秒 | `DECIMAL(6,2)`（时长）/`DECIMAL(7,2)`（资产） | `Decimal` | `string` |
| 时间 | `DATETIME(3)` | `datetime`（UTC aware） | `string`（ISO） |
| 布尔 | `TINYINT(1)` | `bool` | `boolean` |
| 短枚举 | `VARCHAR(24)` + `CHECK` | `StrEnum` | `as const` 联合 |
| 长文本 | `TEXT`(64KB) / `MEDIUMTEXT`(16MB) | `str` | `string` |
| 结构 | `JSON` | pydantic model | 接口/类型 |
| 哈希 | `CHAR(64)` | `str` | `string` |

`MEDIUMTEXT` 用在哪：`episode.synopsis`（真实 4.6–20.9 KB）、`clip.prompt`（真实单片段正文约 2–4 KB）、`revision.prompt`、`skill_version.body_md`（真实一篇终剪提示词 168 KB，**必须留余量**）。

## 3. JSON 列 schema

以下每个 JSON 列都**必须有 pydantic model 对应**，写入前校验，读取后校验（防历史脏数据）。

### 3.1 `clip.ref_slots_json`

```json
[
  { "idx": 1, "kind": "image", "asset_id": 41, "role": "实景",   "note": "荒郊猪窝泥潭夜景，全片段唯一实景" },
  { "idx": 2, "kind": "image", "asset_id": 12, "role": "造型锚", "note": "徒弟造型锚点" },
  { "idx": 1, "kind": "video", "asset_id": 88, "role": "形态参考", "note": "上一段化形的连续中间体" }
]
```

约束：
- `idx` 是该 `kind` **内部的序号**，从 1 连续（对应上游 `ref_image_0..N` / `ref_video_0..N` / `ref_audio_0..N`）。
- `kind ∈ {image, video, audio}`；`asset.kind` 必须与 `kind` 一致；`asset` 必须属于同一 `project`。
- 数量上限由**当前调用的模型**决定，见 §3.8。**不写全局常量** —— 真实第一集最多用到 6 张图，但 seedance-2.0 支持 9 张，按 6 限会把能力关掉。
- `asset_ref`（可选字符串）是**未回填槽位的占位**：seed 导入时 `skN_*.png` 只是 `_krea2_pipeline` 的作业副本名，本目录里没有对应 `asset`，于是 `asset_id` 为 `null`、`asset_ref` 留原文件名，等资产库按导出作业回填（§8.4 第 4 条）。`asset_id` 非空时 `asset_ref` 可为空。
- `script_ref`（可选字符串）记录这个槽位是从剧本哪条「参考资产」回填来的（如 `01场景-荒郊猪窝-泥潭夜景`），用于追溯与人工复核；回填成功后 `asset_id` 非空，`script_ref` 保留证据。
- `url` / `thumb_url`（可选字符串）是**出参派生**的取图地址，`asset_id` 非空时由服务端填；**不落库**（存下来换存储后就成死链），写入前由 `_strip_derived` 剔掉。

### 3.2 `clip.shots_json`

```json
[
  { "no": 1, "start": 0.00, "end": 3.50, "desc": "极远景急推至中景…", "camera": "连续急推，全程不停" },
  { "no": 2, "start": 3.50, "end": 6.50, "desc": "硬切，界面即画幅…",   "camera": "静态展示" },
  { "no": 3, "start": 6.50, "end": 9.00, "desc": "界面内部缓慢上推…",   "camera": "内部上推右移" },
  { "no": 4, "start": 9.00, "end": 12.00,"desc": "硬切回猪窝，低角度贴脸特写","camera": "随撑起上抬后撤" }
]
```

约束：`no` 从 1 连续；`start[0] == 0`；`end[i] == start[i+1]`；`end[last] == clip.duration_s`（容差 ±0.05 s）；`end > start`；最多 8 个镜头。

### 3.3 `clip.dialogue_json`

```json
[
  { "speaker": "system", "text": "恭喜宿主完成任务——给单身八百年的母猪妖接生并伺候月子！", "shot_no": 2, "on_screen": false },
  { "speaker": "徒弟",   "text": "退钱！！！日尼玛退钱！！！",                            "shot_no": 1, "on_screen": true }
]
```

约束：`text` 是**原文**，不得是摘要（`经验教训.md` #94：正文没词模型就自己编）；`shot_no` 必须存在于 `shots`；单条 ≤200 字；台词总字数 ÷ 时长 落在 4–6 字/秒为合格（不硬拦，仅评测计分）。

**`dialogue_json` 是抽取结果，不是唯一真相**：真实数据里片段3 根本没有 `- **台词**` 段，三句词全内嵌在提示词正文（其中一句还用 `{…}` 包裹）。所以：
- 结构化的 `dialogue_json` 优先取台词段；缺失时从 `prompt` 正文按 `「…」` / `{…}` 反抽；
- 无论哪种来源，**每条台词都必须在 `clip.prompt` 里逐字出现**，否则 `422 VALIDATION_INVARIANT`（这条规则拦的正是 #94 的事故）。

### 3.4 `clip.acceptance_json` / `revision.acceptance_result_json`

```json
[
  { "id": "a1", "criterion": "功德环全程可见且为实体金环，非虚化光晕", "superseded_by": null },
  { "id": "a2", "criterion": "母猪妖全程侧躺，绝不起身",            "superseded_by": null }
]
// revision.acceptance_result_json —— 质检后回填
[
  { "id": "a1", "result": "pass", "evidence": "0.0s/4.5s/9.0s 抽样帧均可见" },
  { "id": "a2", "result": "fail", "evidence": "6.2s 起身" }
]
```

约束：`id` 在同一 clip 内唯一；`result ∈ {pass, fail, unknown}`；`criterion` ≤200 字，必须是**可判定的陈述**（"画面好看"不行）；`superseded_by` 指向取代它的 `id`（**真实数据里验收点会随版本改判**：片段7 的「两人各露八颗白牙」因与氧气罩造型互斥，已被「师尊露八颗、徒弟隔着罩同样咧到最大」取代，见 `经验教训.md` #115）。被取代的判据**不参与质检打分**，只留档。

### 3.5 `revision.motion_json`

```json
{ "samples": 23, "freeze": 0, "avg": 29.82, "max": 51.20, "flagged_at": [] }
```

来源 `video-motion-review` 的 `vscan.ps1`。**`freeze > 0` 只产生提示，不自动判 fail**（SKILL 的硬规矩：运动是三诊信号不是判决）。

### 3.6 `skill_version.sections_json`

```json
[
  { "rule_id": "#110", "title": "巨物压迫感四件套", "tags": ["巨物", "压迫感", "开场"],
    "text": "…", "tokens_est": 380 },
  { "rule_id": "#112", "title": "机位位移＋背景相对位移", "tags": ["运镜", "背景"],
    "text": "…", "tokens_est": 210 }
]
```

约束：`rule_id` 唯一；`tags` 用于召回打分；`tokens_est` 由 `len(text)//2` 估算，用于预算裁剪（`03` §4.3）；单节 `text` ≤2000 字。

### 3.7 `revision.params_json` / `job.error_detail`

```json
// params_json
{ "res": "720p", "aspect": "16:9", "duration_s": "12.00", "seed": 0, "mode": "draft" }
// error_detail
{ "provider": "seedance", "http_status": 429, "retry_after_s": 12, "raw": "…(截断 2000 字)" }
// 产物下载失败时额外带（内部字段，见下）
{ "resume": "asset_fetch", "output_url": "https://…" }
```

`raw` 仅供排查，**永不进 `message`**，前端默认折叠。`output_url` 是带签名的下载直链（能力型字段：拿到即可下载），**永不返回 API**，只进服务端日志与补拉流程（`03` §3.1）。

### 3.8 模型参考容量表（provider 配置，不是 domain 常量）

| 模型系列 | 图片参考 | 视频参考 | 音频参考 | 备注 |
|---|---|---|---|---|
| `seedance-2.0`（含 mini / 720p / fast） | **9** | **3** | **3** | 真实第一集用的是 `seedance-2.0-mini`，最多用到 6 张图 |
| `seedance-2.5` | **30** | **10** | **10** | 换系列即换容量，代码不感知具体数字 |
| `gemini-3.1-flash-image-preview` | **10** | 0 | 0 | 锁定 10 张 |
| `gpt-image-2.5`（flare / sunburst） | **10** | 0 | 0 | 锁定 10 张 |

规则：
1. 容量表存在 provider 配置（`GET /admin/providers` 可见），**校验时读当前 `model_requested` 的容量**，不在 domain 里写死。
2. 超容量 → `422 MODEL_REF_LIMIT`，`detail` 带 `{kind, used, allowed, model}`，让用户知道该加图还是该换模型。
3. 降级到另一个模型时**必须重新校验容量**：seedance-2.5（30 图）失败降级到 2.0（9 图）时，原请求可能直接不合法。
4. 图片/视频/音频三类槽位分开计数，互不占用额度。

### 4.4 clip

```sql
CREATE TABLE clip (
  id                  BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  episode_id          BIGINT UNSIGNED NOT NULL,
  idx                 INT UNSIGNED    NOT NULL,   -- **播放顺序** 1-based，不是源片段号
  source_idx          INT UNSIGNED    NOT NULL,   -- 源文件里的「片段N」；插入镜时与 idx 不同
  title               VARCHAR(200)    NULL,       -- 片段标题（分镜表标题列）；给了就不能是空白串
  duration_s          DECIMAL(6,2)    NOT NULL,
  status              VARCHAR(16)     NOT NULL DEFAULT 'draft',
  prompt              MEDIUMTEXT      NULL,
  negative            TEXT            NULL,
  ref_slots_json      JSON            NULL,
  shots_json          JSON            NULL,
  dialogue_json       JSON            NULL,
  acceptance_json     JSON            NULL,
  current_revision_id BIGINT UNSIGNED NULL,       -- 无 FK，见 §5.3
  parent_clip_id      BIGINT UNSIGNED NULL,       -- 替换件指向原片段
  version             INT UNSIGNED    NOT NULL DEFAULT 1,
  created_at          DATETIME(3)     NOT NULL,
  updated_at          DATETIME(3)     NOT NULL,
  -- 生成列：只有"非替换件"参与 idx 唯一，替换件可与原片同 idx
  -- 必须 VIRTUAL，不能 STORED：MySQL 禁止「STORED 生成列的基列上带 ON DELETE SET NULL 的外键」，
  -- 而 parent_clip_id 正是 SET NULL（实测报 1215 Cannot add foreign key constraint）。
  idx_key INT UNSIGNED GENERATED ALWAYS AS (IF(parent_clip_id IS NULL, idx, NULL)) VIRTUAL,
  PRIMARY KEY (id),
  UNIQUE KEY uk_clip_ep_idx (episode_id, idx_key),
  KEY idx_clip_status (episode_id, status, id),
  KEY idx_clip_parent (parent_clip_id),
  KEY idx_clip_rev (current_revision_id),
  CONSTRAINT fk_clip_ep     FOREIGN KEY (episode_id)     REFERENCES episode(id) ON DELETE CASCADE,
  CONSTRAINT fk_clip_parent FOREIGN KEY (parent_clip_id) REFERENCES clip(id)    ON DELETE SET NULL,
  CONSTRAINT ck_clip_status CHECK (status IN ('draft','prompted','generating','review','approved','rejected')),
  CONSTRAINT ck_clip_dur    CHECK (duration_s BETWEEN 1.00 AND 15.00),
  CONSTRAINT ck_clip_idx    CHECK (idx BETWEEN 1 AND 30)
);
```

> **`idx` 是播放序，不是源片段号。** 真实第一集终剪有 8 个片段，但剧本只有 7 段：`片段8` 是插入镜（交付名 `s6b_徒弟的自嘲反应.mp4`），播放位置在 `s6` 之后、`s7` 之前。若把 `idx` 当源序号用，剪辑顺序就会把插入镜排到最后。
>
> `idx_key` 的必要性：替换件（真实产物里的 `s3b_`、`s6a_`）在同一集、序号与原片相同，普通 `UNIQUE(episode_id, idx)` 会撞。用 `NULL` 不参与唯一比较的特性避开，无需改业务字段。已实测：带 `parent_clip_id` 的同 idx 插入成功，第二个非替换件被 `uk_clip_ep_idx` 拒绝。

### 4.5 asset

```sql
CREATE TABLE asset (
  id          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  project_id  BIGINT UNSIGNED NOT NULL,
  kind        VARCHAR(16)     NOT NULL,
  path        VARCHAR(512)    NOT NULL,          -- 相对 MEDIA_ROOT，禁止绝对路径
  thumb_path  VARCHAR(512)    NULL,              -- 缩略图相对路径；为空时取图回落到 path
  sha256      CHAR(64)        NOT NULL,
  bytes       BIGINT UNSIGNED NOT NULL,
  w           INT UNSIGNED    NULL,
  h           INT UNSIGNED    NULL,              -- 原片尺寸
  thumb_w     INT UNSIGNED    NULL,              -- 海报尺寸（长边 ≤720），与 w/h 不是一组数
  thumb_h     INT UNSIGNED    NULL,
  dur_s       DECIMAL(7,2)    NULL,
  source      VARCHAR(16)     NOT NULL,
  revision_id BIGINT UNSIGNED NULL,              -- 无 FK，见 §5.3
  created_at  DATETIME(3)     NOT NULL,
  PRIMARY KEY (id),
  UNIQUE KEY uk_asset_sha (project_id, sha256),
  KEY idx_asset_list (project_id, kind, id),
  KEY idx_asset_rev (revision_id),
  CONSTRAINT fk_asset_project FOREIGN KEY (project_id) REFERENCES project(id) ON DELETE CASCADE,
  CONSTRAINT ck_asset_kind   CHECK (kind IN ('image','video','audio')),
  CONSTRAINT ck_asset_source CHECK (source IN ('gen','upload','seed'))
);
```

**生命周期**：资产**不级联删**。删除走 `DELETE /assets/{aid}`，被片段槽位或某次 take 的产物引用时
`409 CONFLICT_ASSET_REFERENCED`（`detail.usages` 列出引用方，让人先改哪里）。
物理文件默认保留 —— `MEDIA_ROOT` 就是用户的剧集目录，`seed`/`upload` 素材删了没有第二份；
`?purge=1` 只删 `.gen/` 下的派生文件（我们自己生成的那些），且同路径还被别的 asset 行引用时不删。
项目整体删除时 `ON DELETE CASCADE` 才真正连带清掉资产行（文件仍留在盘上，由人决定）。

### 4.7 job

```sql
CREATE TABLE job (
  id           BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  kind         VARCHAR(16)     NOT NULL,

### 4.13 event_log（SSE 跨副本事件日志，迁移 `0008` + `0009`）

```sql
CREATE TABLE event_log (
  id         BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,   -- 就是 SSE 的 Last-Event-ID（全局自增）
  project_id BIGINT UNSIGNED NOT NULL,
  name       VARCHAR(48) NOT NULL,                      -- job.updated / clip.updated / cost.updated …
  payload    JSON NOT NULL,
  created_at DATETIME(3) NOT NULL,
  PRIMARY KEY (id),
  KEY idx_event_project_seq (project_id, id)
  -- 故意没有 project 外键：见下面"为什么没有 FK"
);
```

**为什么没有 FK**：`publish` 常常发生在已持有 `project` 行锁的事务里（`submit` / `confirm`），
而 FK 校验要给父行加 S 锁 —— 会等自己那把 X 锁，直到 `lock wait timeout`（实测 30 s，
异常被吞后表现为"接口变慢、事件没落库"）。日志是**投递通道**不是账本：孤儿行由 `EVENT_KEEP_DAYS` 清理。

**为什么需要一张表**：进程内总线只在本副本可见。多副本时别的副本发的事件收不到，
表现是"任务卡住、刷新一下才更新"。`id` 作为全局序号保证任意副本都能按 `Last-Event-ID` 续传。
保留 `EVENT_KEEP_DAYS` 天（**不是审计日志**：钱看 `revision`、终态看 `job`），
每发布 `EVENT_PRUNE_EVERY` 条顺手清一次。

## 5. 关系与约束策略

### 5.1 ER（文字）

```
user 1─n project(owner)           user n─n project(project_member)
project 1─n episode 1─n clip 1─n clip(替换件, self)
project 1─n asset
revision n─1 (target: clip|episode|project|skill)  ← 多态，无 FK
revision 1─1 asset(output)         asset n─1 revision(产出者)  ← 循环，均不建 FK
job n─1 (target: clip|episode|skill_version)       ← 多态，无 FK
skill 1─n skill_version
```

### 5.2 `owner` 只存在一处

`project.owner_id` 是所有权**唯一真相**；`project_member.role` 只取 `member` / `viewer`，**不存 owner**。避免"两处表都能说自己是 owner"的漂移。所有权在 v0 不可转移。

### 5.3 三个刻意不建外键的地方

| 列 | 为什么 |
|---|---|
| `revision.target_id` / `job.target_id` | 多态指向 4 张表，FK 无法表达 |
| `asset.revision_id` ↔ `revision.output_asset_id` | **互相引用成环**，级联删除会成环报错。两条都只建索引，由 service 在同一事务里维护 |
| `clip.current_revision_id` | 指向"某条 revision"，而 revision 又可能被回滚/替换；建 FK 反而使删除顺序不可控 |

兜底：`scripts/check_orphans.sql` 放三个 `LEFT JOIN … IS NULL` 查询，进 CI，发现孤儿即失败。

### 5.4 domain 层不变量（写入前必校验，DB 不表达）

| 不变量 | 校验点 |
|---|---|
| `shots` 首镜 `start = 0`、逐镜首尾相接、末镜 `end == duration_s ±0.05` | `clip` 保存 & 生成前 |
| `ref_slots.idx` 各 `kind` 内从 1 连续、role 合法、asset 同项目且 kind 一致、**数量不超当前模型容量（§3.8）** | `clip` 保存 & 生成前 & 降级换模型后 |
| `dialogue.shot_no ∈ shots[].no`、`text` 非空、非摘要、**逐字出现在 `prompt` 中** | 生成前 |
| `acceptance.id` 唯一、`criterion` ≤200 字 | 生成前 |
| `cost == unit_price × (video_seconds \| tokens)` | 写入 `revision` 前 |
| 状态机迁移合法（见 `02` §6） | 每次状态变更 |

落地方式：`manju/domain.py` 放纯规则（不碰 DB/HTTP，返回问题列表），`manju/clip_rules.py` 补齐需要查库的部分（asset 是否同项目、kind 是否一致）并一次性抛 `VALIDATION_INVARIANT`。五处实现口径必须写清，否则很容易"校验了但流程走不通"：

1. **空 `shots` 只在 `draft` 允许**。迁到 `prompted`（分镜完成）时强制非空 —— 否则"先建片段、后补分镜"这个正常流程会被卡死；一旦填了镜头就必须闭合，不因为是 draft 就放过。
2. **台词内嵌在 `prompt` 为空时跳过**。那是"提示词还没写"的中间态；有 `prompt` 就必须逐字出现（拦的正是 `经验教训.md` #94 的事故）。
3. **槽位数量上限需要模型上下文**。`clip` 保存时还不知道要用哪个模型，所以传 `capacity=None` 只审结构（序号连续、每槽有 `asset_id` 或 `asset_ref`）；真正的容量校验在生成前按 `model_requested` 做（§3.8）。
4. **`cost` 等式只能到半个最小单位**。`unit_price` 存 6 位小数，容差 = 数量 × 0.5e-6。真实样本 12 s / 2.27 元：`unit_price=0.189167`，乘回去 2.270004，差 4e-6 < 6e-6，通过。
5. **同状态迁移视为幂等**。`PATCH` 重复提交不该报错；非法跳转（`draft → approved`）才回 `409 JOB_STATE_INVALID`。

## 7. 迁移纪律

1. Alembic，`asyncmy` 方言。**只允许**：`CREATE TABLE` / `ADD COLUMN NULL` / `CREATE INDEX`。
2. 禁止：改列类型、改列名、加非空列（需分两步：先加可空 → 回填 → 另一次迁移加约束）、`DROP` 生产列。
3. MySQL DDL 非事务性 → 每条迁移**必须可重复执行**（先查 `information_schema` 再建），CI 对空库跑全量迁移两遍。
4. 迁移前 `mysqldump --single-transaction` 快照；快照路径写进 `migrations/README`。
5. `alembic downgrade` 只在本地开发用，生产不提供回滚脚本（只前滚）。

### 7.1 落地细节（已实测）

| 项 | 做法 | 原因 |
|---|---|---|
| `0001_initial_schema` | 由 `Base.metadata.create_all(checkfirst=True)` 建，**不手抄 13 段 CREATE TABLE** | 手抄副本一定会在第二次改字段时与模型漂移；`checkfirst` 让"表已建、`alembic_version` 未写"的半应用状态可重跑（规则 3） |
| 后续迁移 | `alembic revision -m …` 生成**显式 DDL** | 不要再沿用 0001 的整库同步；加**新表**时用 `<Model>.__table__.create(checkfirst=True)` 只建那一张（`0006_job_trace` 即如此），不碰其它表 |
| `migrations/env.py` | 连接串从 `manju.db.database_url()` 注入 | DSN 只存在一处（`DATABASE_URL`） |
| `alembic.ini` | **纯 ASCII** | alembic 用 locale 编码读 ini，中文注释在 GBK Windows 上直接 `UnicodeDecodeError`（已踩） |
| 一致性守门 | `alembic check` 必须输出 `No new upgrade operations detected` | 模型 ≠ 库时立刻暴露 |
| 往返验证 | `downgrade base` → `upgrade head` → 再灌库 | 已验证 14 表全删全建、数据可重灌 |
| 后端包名 | **`manju`**，不叫 `app` | 工作台正好落在 ComfyUI 树内，ComfyUI 自己的 `app` 包会抢先命中 `sys.path`（实测 pytest 直接 import 到 ComfyUI 的 `app`）。另外 `apps/api/pytest.ini` 自带 rootdir，防同类配置串门 |

跑法（`apps/api` 为工作目录，或 `-c apps/api/alembic.ini`）：

```bash
python -m alembic -c apps/api/alembic.ini upgrade head
python scripts/seed_project.py --load        # 灌真实第一集
python -m alembic -c apps/api/alembic.ini check
cd apps/api && python -m pytest -q           # 含 03 §5 ↔ constants.py 漂移检查
```

数据层依赖只有三个：`sqlalchemy`、`alembic`、`pymysql`。驱动暂用 `pymysql`（纯 Python、免编译）——
`asyncmy` 目前没有 cp313 的 wheel，等 FastAPI 侧真正需要并发时再换 URL 前缀，模型不受影响。

## 8. 种子解析契约（真实第一集 → DB）

`scripts/seed_project.py` 必须**确定性**解析，失败报 `文件:行号`，不得静默跳过。

### 8.1 权威性顺序

```
终剪提示词 > 剧本分镜 > 分集剧情
```

终剪提示词是真正发给模型的最终文本，时长/镜头/槽位都实测过；剧本是它之前的设计稿。实测差异：**剧本 7 段、终剪 8 段**（`片段8` 是插入镜），**6 个片段时长比剧本计划长出 2–6 s**（剧本「约 10s」→ 终剪 12.00 s）。差异只记 report，**不报错**。

### 8.2 匹配与排序（都不能用序号）

- **片段与剧本按标题匹配，不按序号**。去标点去引号后比对；终剪独有的段落 `inserted=true`（真实数据：`片段8 插入片段·徒弟的自嘲反应`）。
- **`idx` = 播放顺序，取自交付名**而非源序号：`第一集\s6b_…` → 排在 `s6` 之后。真实数据里 `片段8` 播放第 7 位、`片段7` 第 8 位。
- 源片段号单独落 `source_idx`。

### 8.3 字段解析锚点

| 源文件 | 目标 | 锚点 |
|---|---|---|
| `人物设定.md` | `project.logline` + characters | `**女主：** …` 三段式 |
| `第N集剧情.md` | `episode.synopsis` | 全文，无结构 |
| `第N集\剧本.md` | `episode.title` / `camera_note` / 参考资产 / 台词对照 | `### Clip K：标题（约 10s）`；`- **参考资产**`；`- **镜头时序（10s）**`；`- **台词与声音**`；`- **运镜**` |
| `第N集\Seedance2.0终剪提示词.md` | `clip.prompt` / `negative` / `ref_slots` / `shots` / `dialogue` / `acceptance` / `revision` | `## 片段K：…（时长：12.00s）`；```` ``` ```` 围栏内正文；`- **参考图槽位**：`ref_image_0=…``；正文里的 `镜头N（起-止秒）：`；`- **台词**`；`- **实测经验（… · v1）**` |
| `00_静态资源\*`、`人物卡\results\*`、`第N集\*.mp4` | `asset`（`source='seed'`） | 文件名前缀：`00人物-` / `01场景-` / `02道具-` |

### 8.4 首次真实运行的结果（2026-10-18）

`episodes=1 clips=8 shots=34 slots=36 dialogue=21 acceptance=13 revisions=17 assets=80 errors=0`

四条必须知道的坑（都是真实数据里踩到的）：

1. **台词不一定有 `台词` 段**：片段3 三句词全内嵌在正文里，其中一句用 `{…}` 包裹。抽取要能兜底（见 §3.3）。
2. **验收点写法不统一**：只有 3/8 个片段能机读（`「…」`、`验收点一：…`、带括注改版），其余是散文结论。→ S4 模板**必须强制输出 acceptance 列表**，否则质检没有判据。
3. **验收点会随版本改判**：片段7 有 5 条，其中 2 条已被取代（§3.4 `superseded_by`）。
4. **槽位文件不在剧集目录**：36 个 `skN_*.png` 是 `_krea2_pipeline` 的作业副本。资产库必须在 W1 支持「按导出作业回填 asset_id」，否则参考图指派全是死链。

**可机读的实测经验是白捡的成本台账**：`TASK_ID` / `input_tokens` / `video_seconds` / `cost` / `latency_ms` / 动线（`samples/freeze/avg/max`）全部抽出来了（17 条，如 12 s → 260,100 tokens → 2.27 元），直接当 §9 的黄金样本与 Mock fixture。

产出统计必须打印：`episodes=N clips=N shots=N slots=N dialogue=N acceptance=N revisions=N assets=N errors=0`。**`errors > 0` 即视为失败**。

### 8.5 落库（`--load`）规则

`scripts/seed_project.py --load` → `apps/api/manju/seed.py`。**天然键幂等**，重跑不产生第二份：

| 表 | 天然键 | 重跑行为 |
|---|---|---|
| `user` | `email = seed@example.com` | 复用；`pwd_hash` 写不可用值 `!seed-no-login`，任何登录都命中不了 |
| `project` | `(owner_id, title)` | 复用，刷新 `genre/tone/logline` |
| `episode` | `(project_id, idx)` | 复用，刷新 `title/synopsis` |
| `clip` | `(episode_id, idx)`（走 `uk_clip_ep_idx`） | 复用，刷新 prompt / 四组 JSON |
| `asset` | `(project_id, sha256)`（走 `uk_asset_sha`） | 复用，不重算不重插 |
| `revision` | `JSON_EXTRACT(params_json,'$.task_id')` 或 `$.version` | **已存在就跳过**（append-only 表，重跑绝不能追加） |

**故意留空的字段（不是 bug，是数据本身没有）：**

- `ref_slots_json[].asset_id` 回填不了的部分（当前 36 个槽位里回填了 17 个），`asset_ref` 留原作业副本名；
- 非最新版 `revision.prompt` = `NULL`：真实数据里只留了终稿正文，编一份早期正文比留空更糟；
- `asset.thumb_path` = `NULL`：缩略图还没生成，取图端点会回落到原图。

**两处连线（`--load` 里做的，不是解析器猜的）：**

| 连线 | 规则 | 现状 |
|---|---|---|
| 剧本参考资产 → `ref_slots[].asset_id` | 剧本「参考图一/二/三」的名字精确匹配到 `00_静态资源` / `人物卡\results` 的真实文件主干；**对到哪个槽位按词元重叠**，不按序号（剧本 3 个资产 vs 终剪 4 个槽位，序号在第 3 个就错位） | 17/36，未匹配的都留警告 |
| 交付成片 → `clip → current_revision → output_asset_id` | 解析器给出交付名主干（`s7` / `s6b`），按 `<主干>_` 前缀找 `第一集/*.mp4` | 8/8 全部连上 |

> 交付名主干是三种编号里唯一可靠的：`片段8`（源序号 8）播放第 7 位、文件名叫 `s6b_`。按序号、按播放位、按标题都会错，只有文件名是真相。

**反算出来的字段：** `unit_price = cost / video_seconds`（两者都有值时才填，保留 6 位小数），
这样 §5.4 的 `cost == unit_price × seconds` 不变量在 seed 数据上成立；
`created_at` 取 `TASK_ID`（`cgt-YYYYMMDDHHMMSS-…`）里的真实提交时刻，而不是导入时刻。

**实测结果（MySQL 8.0.44 与 8.4.11 各跑一遍，结果一致）：**

```
首跑：project=1 episode=1 clip=8 asset=80 revision=17
      slots_resolved=17 slots_unresolved=19 clips_with_output=8 output_missing=0
重跑：project=0 episode=0 clip=0 asset=0 revision=0 revision_skipped=17
加 --thumbs：thumbs_made=19 thumbs_failed=0；再跑 thumbs_reused=19
      海报落在 MEDIA_ROOT/.thumbs/<sha前12位>.jpg，19 张共 884 KB（平均 47 KB）
台账：revision 17 行 / cost 合计 40.00 元 / 4,572,900 tokens / 211 s
      unit_price 0.189–0.192 元/秒（与 §9 成本模型的 0.19–0.20 一致）
```

`asset.thumb_path` 由 `--thumbs` 填；不开这个开关时保持 `NULL`，`GET /assets/{id}/file?thumb=1`
会回落到原片并标 `X-Thumb-Fallback: 1`（`02` §3.9）。抽帧只写 `.thumbs/` 隐藏目录，不碰原始素材。

这 40 元就是第一集的真实生产开销（含 17 次尝试），可直接当 README 里的成本样本。

## 9. 容量估算（决定要不要分表）

单项目：集 ≤ 20（硬上限 50）、每集 clip ≤ 12（硬上限 30）、每 clip revision ≤ 5×attempts ≈ 15。
→ 单项目 `revision` 量级 **≤ 6000 行**，`job` 同量级。**无需分区、无需归档**，一次分页查询即够。
真实第一集反算：7 clip × 约 3 版 ≈ 21 行 `revision`。
