# 04 · 对抗性探针与缺陷记录

> 上游：`03`（异常分层与边界值）。这份文档记的不是"我实现了什么"，而是**我试图把系统弄坏时它怎么反应**。
> 用例在 `apps/api/tests/test_adversarial*.py`，共 164 条；原则写在每个文件头，一句话：
> **客户端能发到的输入返回 5xx 就是缺陷；内部函数吃脏数据只许抛 `ApiError`，不许 `KeyError`。**

## 2. 撞出来的缺陷（都已修，每条留一个用例）

| # | 症状 | 根因 | 修法 | 用例 |
|---|---|---|---|---|
| 1 | 非法 UTF-8 请求体 → **500** | `json.loads` 抛的是 `UnicodeDecodeError`，FastAPI 只捕 `JSONDecodeError`，漏过去变成未处理异常 | `_guard_body` 在缓冲 body 时先 `decode("utf-8")`，失败 `422 body_not_utf8` + 位置 | `test_non_utf8_and_broken_json_body` |
| 2 | `budget_limit: "0"` 被换成默认 12 元 | `payload.budget_limit or BUDGET_JOB_DEFAULT` —— `Decimal("0")` 是假值 | 改 `is not None` | `test_generate_with_absurd_budgets` |
| 3 | 已排队/已跑完的 job 再 `confirm` 回 **200** | `_transition` 把"同状态"当幂等，`queued → queued` 直接放行 | `confirm` 先要求源状态是 `waiting_confirm`，否则 `409`（付费确认不能"看起来又授权一次"） | `test_confirm_on_queued_job_is_409` |
| 4 | 幂等键含空格/斜杠/中文被静默接收 | 路由只判了长度，`03` §8.1 的字符集没接线 | `RE_IDEM.fullmatch` | `test_idempotency_key_charset_is_enforced` |
| 5 | provider 账单自相矛盾时 **钱花了、台账没有** | `enforce_cost` 在 `session.add(revision)` 之前抛，savepoint 回滚把最该记账的那次调用一起丢了 | 先落 revision 与 `cost_used`，再校验；不一致只把 job 停在 `failed` 等人工核账 | `test_lying_bill_keeps_revision_and_fails_job` |
| 6 | DB 里缺键的 `shots_json` → **500 `KeyError`** | `domain` 直接 `shot["no"]`，默认 JSON 列干净 | 四个不变量函数前置 `_missing()`，缺键回一条 `脏数据` problem → `422` | `test_domain_survives_malformed_rows`、`test_dirty_shots_json_is_422_on_step` |
| 7 | 历史验收点缺 `criterion` → worker `KeyError` | `review.judge` 用 `item["criterion"]` | `.get()` + 缺判据记 `unknown`（**不猜**） | `test_dirty_acceptance_json_does_not_kill_worker` |
| 8 | 成本端点可要 20 年区间打全表 | `TIME_RANGE_MAX_DAYS` 只在 `constants.py` 与 `03` §6.2 存在，代码没接线 | `project_cost` 判跨度 | `test_cost_rejects_oversized_range` |
| 9 | Windows 上 ffprobe 输出解码在 reader 线程里炸（`UnicodeDecodeError`，被 `ValueError` 兜住但留下未处理线程异常） | `subprocess.run(text=True)` 用了平台默认编码 | 显式 `encoding="utf-8", errors="replace"` | 由 `test_dirty_acceptance_json_does_not_kill_worker` 的线程警告暴露 |

第 5 条最值得讲：**它只在"上游骗人"时出现**，正常路径永远测不到 —— 而恰恰是这类调用最需要台账。

## 3. 撞了但**不改**的（刻意行为，用例把它钉住）

| 现象 | 为什么保留 |
|---|---|
| 任意登录用户能读任意项目的资产 | `02` §2.2 明写"读任意项目"，v0 的产品决定；写才按项目收口。演示给外人看要留意 |
| 出参侧放过 `duration_s="0"` 这类越界值 | 出参只挡形状：一条历史脏行不该把整个列表端点打成 500。范围由 domain 在写入时拦 |

| 资产路径越界回 `500 INTERNAL` | 这是被篡改的 DB 行，不是客户端输入；但它**绝不会**把 `MEDIA_ROOT` 外的文件吐出去（有用例断言内容不出） |

## 6. 第二轮：按缺陷类型撞（黑/白盒 + 并发 + 授权 + 配置）

第一轮按"输入形状"撞；这一轮按**缺陷类型**撞，每类都要给出"撞法 / 结论"，
撞不出东西也要写清为什么（否则下一轮会重复劳动）。

| 类型 | 撞法 | 结论 |
|---|---|---|
| 空捕获 / 裸捕获 | 扫 `except`：无 `pass`-only，worker 循环的 `except Exception` 有 `logger.exception` | 无缺陷 |
| 注入（SQL/命令/路径） | 扫 `shell=True`/`eval`/`exec`/`pickle`/f-string SQL → 0 命中；PowerShell 参数走单引号转义（`_quote`）；ffmpeg 全用参数数组 + 数值滤镜；`_resolve` realpath 收敛 | 无缺陷（已有 `../` 用例） |
| 缺少超时 / 资源边界 | 扫 `subprocess`：6 处全带 timeout（15/60/120/1800）；httpx 全带 timeout；body 读取 30 s；DB `connect_timeout=5, read_timeout=30, write_timeout=30` | 无缺陷 |
| 异步处理 | 唯一 async 路径是 lifespan/worker/SSE；阻塞调用全在 `to_thread`（`_drain`）；SSE 订阅在 `finally` 里退订、队列 `maxsize=SSE_BUFFER` | 无缺陷 |
| 隐蔽资源泄漏 | 会话走依赖注入；`with Session(...)` 的短会话语义；SSE 断连后订阅者被移除（有用例断言） | 无缺陷 |
| 认证 / 授权 | **全路由枚举**（OpenAPI 取路由表）：未登录逐条打 → 必须 401；viewer 逐条打写路由 → 必须 4xx；admin 打内容写路由 → 必须 4xx（Skill/admin 除外）。三条都成了**常驻用例** `test_authz_sweep.py` | 无缺陷，但补了**系统性守卫**（原来靠人肉 review 新路由） |
| 查询与更新竞态 | 真 uvicorn + 多线程：① 4 路同 sha 并发出图 → 全部 201、同一 asset；② 同 `If-Match` 并发 PATCH → 1×200 + 3×412；③ confirm 与 cancel 同时打 → 终态一致、无挂起（90 s 看门狗） | 见下面第 10 条 |
| 死锁 | 锁序统一是 job → project（`run_job` / `confirm` / `retry` 都先 `_lock_for_queue` 再项目锁）；三组并发探针无挂起 | 无缺陷 |
| 非原子操作 | 逐处审"查了再写"：入仓 by sha256、`_guarded`（带执行令牌的 UPDATE）、`episodes.move`（空槽占位 + 逐行 flush）、`skills._switch`（先腾唯一键槽位） | 见第 10、11 条 |
| 配置错误 | 扫 `int(os.environ[...])` / `Decimal(env)`：坏值会抛 ValueError traceback | 见第 12 条 |
| 验证侵蚀 | 审 pydantic 模型是否被"放宽"：`S5Out.characters` 曾用裸 `list[dict]` → 已收紧为强类型（真模型会漏 `anchor`） | 已修（第一轮遗留项） |

### 本轮撞出来的缺陷

| # | 症状 | 根因 | 修法 |
|---|---|---|---|
| 10 | 并发入仓可能 500 | `generate_image` / `_resolve_output` 都是"查同 sha → 没有就插"，两个请求同时查空后一起插，输的那个撞 `uk_asset_sha` | 用 savepoint 兜 `IntegrityError`，竞败方回读对手那一行（幂等复用）；`deduped=true` |
| 11 | mock 出图在 `.gen/` 留孤儿文件 | mock 先复制一份素材，入仓按 sha 又命中原素材 | mock 直接**指向**原素材，不复制 |
| 12 | 配错整数环境变量 → 裸 traceback | `int(os.environ.get("PROVIDER_TIMEOUT", "120"))` | `_int_env()` 抛"`PROVIDER_TIMEOUT 必须是整数，当前值 '…'`" |

第 10 条是**窗口小、正常测不出来**的那类，所以用例不追求"真并发"（不稳定），
而是**人为把窗口撑开**：让第一次查询假装落空，插入必然撞唯一键，看服务端是否回读 —— 见 `test_races.py`。

### 仍然没覆盖到的

- **多副本**：SSE 总线是进程内的，两个副本之间不互通（已知限制，写在 README 路线图）
- **真上游超时/限流**：只测了适配层的错误分类（`MockTransport`），没打真实超时
- **浏览器端**：渲染与交互没有自动化，只能人眼验收
  （2026-10-19 做过一轮手工对抗性验收：撞出 12 个前端缺陷并修复，见 `05-前端对抗性验收记录.md`）

## 7. 第三轮：业务逻辑层（自愈循环 / 预算 / 归因 / 记忆 / 幂等）

这一轮的问法不是"功能在不在"，而是"**停止条件真的成立吗**"。
共 8 条断言，7 条本来是对的（算作回归防线），**1 条撞出真缺口**。

| # | 断言 | 结果 |
|---|---|---|
| 1 | 永远失败 + 归因可执行 → 恰好跑满 `max_attempts` 次上游调用后转人工 | ✅ 成立（3 次执行、3 条 revision、钱一次不漏） |
| 2 | 归因不出（`fix=None`）→ 一次即 `ESCALATED`，不空转 | ✅ 成立（`attempts=0`、只有 1 条 revision） |
| 3 | 预算在**重试间累积**：1.5 元额度下第二次调用前就停下 | ✅ 成立（`paused_budget`、只花一次） |
| 4 | 预算小于单次预估 → **调用前**就停，零 revision | ✅ 成立 |
| 5 | 同 scope 同因同修只留一行教训，命中次数累加 | ✅ 成立（3 次 → 1 行、`hit_count=3`） |
| 6 | 幂等指纹**含 mode**：同 key 换 mode 必须 409 | ✅ 成立 |
| 7 | **项目日预算**（100 元/项目/天）是一道提交前的闸 | ❌ **缺口**：常量与文档都有，`jobs.submit` 没实现 |
| 8 | 没到日上限时不误伤正常提交 | ✅ 成立（补闸后） |

### 缺陷 13：项目日预算只有声明和文档，代码里没有闸

`03` §7.3 写着"项目日成本达 `BUDGET_PROJECT_DAILY` → 新的生成请求直接 `402`，不做再试一次"，
`constants.py` 也声明了 100 元，但 `jobs.submit` 只校验了**单 job** 上下限 —— 项目当天花超了照样能提交。
修法：`submit` 在 project 锁内、并发检查之后加一道 `_project_spent_today()` 闸，超限 `402 BUDGET_EXCEEDED`
（`detail.scope=project_daily`，带 spent/limit）。

### 缺陷 14（自伤）：`from datetime import time` 遮蔽了 `time` 模块

补上面那道闸时顺手加了 `time.min`，于是 `import time` 被遮住，`_elapsed_ms()` 里的
`time.perf_counter()` 变成 `datetime.time.perf_counter` → **每一个 job 都落 `INTERNAL_STATE`**。
8 条业务逻辑用例当场全红，是全量跑才暴露的（单跑某一组可能看起来只是"偶发失败"）。
修法：`from datetime import time as dt_time`，并在注释里写明"别用 `time`"。

> 这两条一起说明一件事：**业务逻辑层的缺陷往往是"补一个正确的东西时把另一个弄坏"**，
> 所以每轮改完必须跑全量，而不是只跑被改的那组。

## 8. 第四轮：多集 / 跨集口径（钱与一致性）

这一轮专挑"最近才长出来的东西"：多集、跨集复用、集维护。6 条断言里 2 条撞出真缺陷。

| # | 断言 | 结果 |
|---|---|---|
| 1 | 集重排后成本跟着**那一集**走 | ✅ 成立（`第2集 ¥3` → 挪到首位后变成 `第1集 ¥3`，总额不变） |
| 2 | 片段序号按集独立 | ✅ 成立 |
| 3 | 删**有付费产物**的集，不能把已付的钱从台账带走 | ❌ 缺陷 15 |
| 4 | 删**有付费产物**的片段，同上 | ❌ 缺陷 15 |
| 5 | 已有分镜的集重跑 S2，不能静默改写剧情 | ❌ 缺陷 16 |
| 6 | 跨集复用的资产被删除时，把两集都列出来 | ✅ 成立 |

### 缺陷 15：删集/删片段把已付的钱从台账里带走

`revision` 是 `target_kind/target_id` 多态、**没有 FK**；`DELETE /episodes/{eid}` 靠
`clip.episode_id ON DELETE CASCADE` 删掉片段，revision 就变成无主孤儿 —— 而 `cost` 端点
是 join 片段算的，于是**项目成本凭空少一块**，直接违反 `03` §3 的"宁可偏高，不可漏记"。
修法：删集/删片段前查该内容有没有 revision，有就 `409 CONFLICT_HAS_REVISIONS`（新错误码），
把"删了会漏记多少条"写在 `detail.revisions` 里 —— 和资产"被引用即禁删"同一口径。

### 缺陷 16：S2 覆盖已有分镜的集，剧情与分镜静默不一致

S2 只覆盖 `synopsis`，片段原样留着；而 `episode.status` 因为"只进不退"还停在 `storyboarded`，
于是**剧情按新写的、分镜按旧的**，没有任何信号。修法：S2 在 `_write_back` 里先数该集片段，
有片段就 `409 CONFLICT_CLIP_INDEX`（与 S3 同口径：要重来请新建一集）。

> 这两条都属于"**删除/覆盖类操作忘了下游还有账**"，是业务逻辑层最常见的形态：
> 单独看每个接口都对，串起来就漏。
